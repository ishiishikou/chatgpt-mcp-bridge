# Assistant-mediated response receipt: offline prototype

Status: **research only / not attached to an MCP server / no live ChatGPT validation**.

This addresses [Issue #3](https://github.com/ishiishikou/chatgpt-mcp-bridge/issues/3) without sending any ChatGPT messages or requiring production credentials. It is not a replacement for the current normal ChatGPT conversation.

## What is and is not possible

The MCP Apps `ui/message` call lets an iframe ask the host to add a user message to the current chat. Host acceptance does **not** return the assistant's subsequent answer to the iframe or MCP server. `ui/notifications/tool-result` reports the result of an MCP tool invocation, not arbitrary assistant chat turns.

A *potential*, unvalidated alternative is a **model-visible MCP tool** named, for example, `record_bridge_response`. In a permitted one-shot experiment, the user would explicitly ask the assistant to invoke the tool with a fixed acknowledgement and a correlation ID. The MCP server would store the receipt; an authorized external agent could read that record.

This is **not passive conversation access**, and it is not guaranteed that the model will invoke the tool. Even when recorded, it proves only that a permitted tool call was accepted, not that the model supplied all intended content, or that the whole chat transcript was retrieved.

## Offline component contract

`response_receipts.py` is deliberately **not registered** with `server.py`. It cannot send a message, start a tunnel or read ChatGPT. Its SQLite table is a separate experimental ledger under the ignored `state/` directory; it is never auto-created on receipt.

The default state is disabled. Database provisioning requires a private (0700) directory and a non-symlink database opened with owner-only (0600) permissions. SQLite writer connections enforce `synchronous=FULL`; WAL/SHM files stay inside the private directory. If the existing runtime `state/` directory is too permissive, provisioning refuses to proceed until the operator safely provisions a separate private path. A privileged operator must explicitly initialize storage and prepare an event; `prepare_receipt(..., enabled=True)` allows only one event and a TTL of 1–3600 seconds. A later `record_receipt(..., enabled=True, authenticated_principal=...)` accepts **only** the literal `安全送信を受信`, verifies event owner, ensures the event was prepared and not expired, then commits a receipt exactly once in SQLite under `BEGIN IMMEDIATE`. Unmatched, expired, missing-DB, disabled or duplicate requests fail closed. The status reader also requires the same principal.

The `authenticated_principal` argument **must come from verified server-side authentication**, not from tool arguments, text generated by an assistant, HTML, browser headers accepted without validation, or any user-supplied parameter. This prototype has no authentication adapter.

`test_response_receipts.py` is strictly offline; it tests disabled operation, missing DB, successful and persistent registration, wrong/absent principal, wrong phrase, expiry, duplicate/limit, unprepared events, atomic concurrency, and bad identifiers/TTL. Tests use temporary databases.

## Required integration before any real message or public server

1. Verify an actual authenticated MCP connection; derive owner/session identity from a trusted auth context. Deny all anonymous clients and all attempts to pass `authenticated_principal` as model-callable input. Bind the identity to the specific consented chat/session and event.
2. Confirm a legitimate, explicitly user-approved event already has a durable consumed dispatch claim before preparing a receipt. Never reset or replace the existing `dispatch.sqlite3` and do not enable additional sends from this module.
3. Expose only the fixed-phrase response tool to the model with an unambiguous user-approved purpose. No arbitrary text, private chat history or external-AI content is accepted by this POC; external readers must receive owner-scoped status only.
4. Reconfirm the existing no-send default, global claim limit, database retention, authentication boundaries and UI host capability. Do not open the retired `show_auto_probe` or old ChatGPT chat.
5. Obtain **separate explicit authorization** for any single real `ui/message` attempt. Verify actual iframe initialization, correlation, tool invocation, DB receipt and response handling independently. Treat missing callbacks as `unknown`, never automatically resend.
6. Test private server deployment protections (TLS, OAuth audience/scope, CSRF/origin behavior, replay limits and event ownership) before exposing write endpoints publicly.

No deployment, production-ready guarantee, passive assistant-answer capture, or live send is claimed.
